# Conectar el consumidor Barista

El piloto usa dos entradas. Una issue abierta por el autor autorizado se procesa desde la rama predeterminada. Para una PR, un workflow sin permisos ni checkout termina la recepción. El segundo workflow se ejecuta desde la rama predeterminada, recupera por API el run y la PR asociada, valida autor, repositorio, base y head y recupera únicamente el parche AL del caso. El modelo recibe los datos como texto. Los permisos del job son de lectura. Ambos caminos guardan sus resultados como artefactos.

1. Preparar el consumidor con la semilla y los materiales de la [PR de escenarios](https://github.com/javiarmesto/al-knowledge-advisor-smoke/pull/7). La base debe llamarse `main`. Copiar los dos YAML de `consumer-pilot/workflows/` a `.github/workflows/` en esa base. Incorporar las dos claves de `barista-policy.json` a `.github/AL-Go-Settings.json`, conservando sus otras claves. Publicar la base antes de abrir cualquiera de los dos casos.
2. En **Settings → Secrets and variables → Actions → Variables**, definir `ADVISOR_HARNESS_SHA` con el SHA completo del commit del banco de pruebas que contiene este directorio, y `ADVISOR_PILOT_AUTHOR` con el login que abrirá la issue y la PR. La ausencia de `ADVISOR_PILOT_MODE` selecciona la comprobación sin modelo.
3. Abrir primero la issue con su título exacto de la PR de escenarios. Después abrir la PR preparada desde `pilot/barista-export-key` en el mismo repositorio, lista para revisión y con destino a `main`. El diff debe ser el del campo Barista y tener un solo archivo. Para cada evento, comprobar el run **Barista knowledge advisor**, `source.json`, `input.json`, `manifest.json` y `filter-report.json`. En modo offline, el preflight debe dar PASS y el smoke NOT RUN. Una PR sin asociación inequívoca o cuyo head haya cambiado se rechaza.
4. Para probar el modelo, añadir el secreto **del consumidor** `COPILOT_SMOKE_TOKEN` y poner `ADVISOR_PILOT_MODE=live`. Reejecutar el job de confianza para cada evento mientras la issue y la PR siguen abiertas y la PR conserva su head. Cada evento puede abrir dos sesiones de 30 AI Credits. Descargar los dos artefactos y aplicar la rúbrica de escenarios. Volver a modo offline al terminar.

El piloto usa el marketplace público oficial. La etiqueta v1.9 (ce45c5ab) carece de la skill al-knowledge, aunque su manifiesto también dice 1.9.0. La política de ensayo elige explícitamente la rama main de BCQuality. Se comprueba su revisión esperada antes y después de la instalación. Si la rama cambia, se detiene el run para revisar la nueva procedencia. El consumidor pasa a SetupBCQuality sus filtros de capas, skills y artículos. El informe del instalador conserva su identificador de fuente y hash de contenido; el runner registra por separado hashes de los archivos entregados y deja pluginCommit desconocido para una instalación sin Git. Se conserva el modo de clon fijado del smoke anterior.

El ensayo está acotado a un autor, dos entradas y un conjunto revisado de reglas. La automatización no comenta en la issue o la PR. El workflow de comprobación en el banco de pruebas ejercita la acción oficial y los dos formatos de entrada sin utilizar un modelo. No reemplaza el ensayo de eventos en el consumidor.
